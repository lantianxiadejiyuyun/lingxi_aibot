# 番剧下载与文件服务

灵犀使用自己的模型客户端、工具系统和后台任务完成搜索、选源、下载与恢复，不接入 Harness。长时间下载由独立 worker 跟进，网页或飞书会话可以继续聊天。

## 能做什么

- 按名称、别名、季、集、画质和字幕搜索；支持网页、RSS/Torznab RSS、磁力、`.torrent`、HTTP(S) 直链。
- 磁力和种子交给 qBittorrent，HTTP(S) 文件交给 aria2。
- 下载停滞先重试；仍失败时，在任务关联会话中重新调用 AI，带上失败记录搜索新来源。
- 多轮工具调用与内部子代理；每个子代理有独立上下文，受工具权限和共享预算限制。
- 保存到服务器本机硬盘，或宿主机已挂载的 SMB/NFS NAS；网页可以查看目录和下载文件。
- 网页、飞书等现有聊天渠道、REST API 共用同一任务记录；进度事件可以续传。

无需模型常驻等待下载。模型需要支持可靠的工具调用和结构化参数；是否能完成任务取决于实际模型、接口和搜索源，参数量本身不是保证。下载重试和存储检查由程序执行。

## 最短部署步骤

已有 qBittorrent/aria2 时，保留现有下载器，只增加存储映射和 worker。以下以 `docker-compose.quickstart.yml` 为例；现有项目使用其他 Compose 文件时，替换第一个 `-f`，保留原来的项目名 `-p`、端口及数据库配置。

### 1. 准备硬盘或 NAS 目录

在**运行 Docker 的服务器**上操作。不要把电脑的 `E:\` 路径直接填写给另一台 fnOS 服务器。

```sh
# 本机硬盘示例：先建立专用目录，赋予应用使用的 UID 1000 写权限。
mkdir -p /vol1/media/lingxi
chown 1000:1000 /vol1/media/lingxi
export MEDIA_ROOT=/vol1/media/lingxi
test -d "$MEDIA_ROOT" && test ! -L "$MEDIA_ROOT"
```

NAS 先在 fnOS/Linux 宿主机通过 SMB/NFS 挂载，再把 `MEDIA_ROOT` 设为共享目录中的专用子目录。例如 `/mnt/anime/lingxi`。开始部署前确认它确实属于共享挂载：

```sh
export MEDIA_ROOT=/mnt/anime/lingxi
test -d "$MEDIA_ROOT" && test ! -L "$MEDIA_ROOT"
findmnt -T "$MEDIA_ROOT" -o TARGET,SOURCE,FSTYPE
# 使用 NAS 时，必须看到预期的共享来源和 cifs / nfs / nfs4 类型。
case "$(findmnt -T "$MEDIA_ROOT" -n -o FSTYPE)" in
  cifs|nfs|nfs4) ;;
  *) printf '%s\n' 'NAS 尚未挂载，停止启动。' >&2; exit 1 ;;
esac
```

把 `MEDIA_ROOT=实际目录` 写入项目根 `.env`，供 Compose 每次启动读取。SMB 凭据留在宿主机的受限权限凭据文件，应用内只登记路径。Windows 电脑硬盘可以先通过 SMB 共享，再由 fnOS 挂载；电脑关机后任务会等待存储恢复。

叠加配置将同一目录映射为应用和 worker 内的 `/media`，使用 `create_host_path: false`，路径拼错时不会自动建立空目录。NAS 登记后还会生成身份标记，挂载丢失或设备改变时停止写入。NAS 重新挂载后，如果容器仍持有旧 bind mount，重新创建 app、worker 和下载器容器。

### 2. 更新应用并启动 worker

先按现有部署流程备份数据库和 `data/`，然后在项目目录执行：

```sh
docker compose -f docker-compose.quickstart.yml -f docker-compose.media.yml config --quiet
docker compose -f docker-compose.quickstart.yml -f docker-compose.media.yml build app media-worker
docker compose -f docker-compose.quickstart.yml -f docker-compose.media.yml run --rm --no-deps app python -m flask init-db
docker compose -f docker-compose.quickstart.yml -f docker-compose.media.yml up -d app media-worker
```

worker 与 app 使用相同镜像、MySQL 和 `data/.env`。它通过 `python -m flask media-worker --concurrency 3` 启动；不额外启动飞书长连接、网页服务或 APScheduler。不要使用 `reset-db` 更新现有数据库。

### 3. 在「文件与下载」中填写配置

管理员登记存储位置：

| 配置 | 示例 | 含义 |
| --- | --- | --- |
| 存储类型 | 本机 / 已挂载 NAS | NAS 必须先在宿主机挂载 |
| 应用路径 | `/media` | app 与 worker 看见的目录 |
| 下载器路径 | `/media` 或 `/downloads` | **同一实际目录**在下载器容器中的路径 |
| 预留空间 | 默认 256 MiB | 空间不足时等待，不反复换源 |

下载器地址使用容器能访问到的地址。已有宿主机下载器可以填写 `http://host.docker.internal:端口`；其他 NAS 使用其局域网地址。容器内的 `127.0.0.1` 指容器自己。

qBittorrent 填接口根地址、账号、密码；aria2 填接口根地址或 `/jsonrpc` 地址、RPC secret。连接配置和 RSS 中的密钥不会进入 AI 上下文。只有管理员能登记服务器目录或下载器连接；任务和文件按账号隔离。

### 4. 创建一个任务

先使用自己可访问的测试资源验证路径与权限。在网页创建任务，或对机器人说：

> 搜索「番剧名称」第 2 季第 3 集，1080p、简中字幕，保存到我的番剧库；下载失败后自动换源。

任务会返回编号；详情中可以查看候选资源、下载记录、AI 恢复过程，并暂停、继续或取消。通知沿用此账号已配置的飞书等渠道。

## 没有下载器：可选安装

提供 `media-aria2`、`media-qb` 两个 profile，可独立启用。镜像基于 Debian 官方 `trixie-slim`，从发行版仓库安装 [aria2](https://packages.debian.org/trixie/aria2) 和 [qbittorrent-nox](https://packages.debian.org/trixie/qbittorrent-nox)，不运行外部安装脚本。

aria2 的 secret 存成文件；不会出现在 Compose 展开结果或进程参数中：

```sh
mkdir -p data/media
umask 077
openssl rand -hex 32 > data/media/aria2-secret
docker compose -f docker-compose.quickstart.yml -f docker-compose.media.yml \
  --profile media-aria2 --profile media-qb up -d --build aria2 qbittorrent
```

在灵犀填写 `http://aria2:6800` 和 `http://qbittorrent:8080`，两者的下载器路径都是 `/media`。aria2 secret 使用刚生成的文件内容。

qB 首次启动的临时密码由其自身打印到容器日志，查看后在管理界面设为固定密码；该行为见 [qB 官方说明](https://github.com/qbittorrent/qBittorrent/blob/master/doc/en/qbittorrent-nox.1.md)。管理端口只绑定宿主机 `127.0.0.1:18080`。远程管理可以在电脑执行 `ssh -L 18080:127.0.0.1:18080 用户@服务器`，再打开电脑的 `http://127.0.0.1:18080`。完成配置后不要公开此端口。

## 下载器网络隔离

页面、RSS 和种子文件由应用通过现有公网校验、DNS 固定连接和逐跳检查读取。但 aria2/qB 是独立进程，单次 URL 检查无法约束它们后续的重定向、DNS 变化、tracker 或 webseed 请求。

上面的**可选容器已经包含出口规则**：启动时在自己的网络命名空间中安装 OUTPUT 防火墙，允许 Docker DNS 和已建立连接的回包，拒绝内网、环回、链路本地、元数据等地址，并关闭 IPv6。随后降为 UID 1000、清空 capabilities；下载进程不能修改规则。安装规则失败会退出，不带保护启动。它不改宿主机 iptables，也不使用 host 网络。Docker 需要允许容器内的 NET_ADMIN；只在初始化阶段使用该能力。

如果接入**已有下载器**，应在它所在机器或网络命名空间部署同等限制。以下是 Linux Docker 使用 iptables 后端的宿主机参考，必须替换真实下载器容器 IP，并确认宿主策略和 IPv6 情况。`DOCKER-USER` 负责转发流量，`INPUT` 同时拦住下载器主动访问宿主机。官方行为说明见 [Docker iptables 文档](https://docs.docker.com/engine/network/firewall-iptables/)。

```sh
# 示例 IP，替换成实际下载器容器地址；只包含下载器，不要包含 app/worker。
DOWNLOADER_IP=172.30.79.10
iptables -N LX-DOWNLOADER 2>/dev/null || true
iptables -F LX-DOWNLOADER
iptables -A LX-DOWNLOADER -m conntrack --ctstate ESTABLISHED,RELATED -j RETURN
for cidr in 0.0.0.0/8 10.0.0.0/8 100.64.0.0/10 127.0.0.0/8 \
  169.254.0.0/16 172.16.0.0/12 192.0.0.0/24 192.0.2.0/24 \
  192.168.0.0/16 198.18.0.0/15 198.51.100.0/24 203.0.113.0/24 \
  224.0.0.0/4 240.0.0.0/4; do
  iptables -A LX-DOWNLOADER -d "$cidr" -j REJECT
done
iptables -A LX-DOWNLOADER -j RETURN
iptables -C DOCKER-USER -s "$DOWNLOADER_IP" -j LX-DOWNLOADER 2>/dev/null || \
  iptables -I DOCKER-USER 1 -s "$DOWNLOADER_IP" -j LX-DOWNLOADER
iptables -C INPUT -s "$DOWNLOADER_IP" -j LX-DOWNLOADER 2>/dev/null || \
  iptables -I INPUT 1 -s "$DOWNLOADER_IP" -j LX-DOWNLOADER
```

宿主机规则不能拦容器内部的环回请求，因此仍需容器内 OUTPUT 规则，或使用本项目提供的隔离下载器。若保留 IPv6，需要对应的 IPv6 出口规则；不能只配置 IPv4。检查 `bridge-nf-call-iptables` 和 Docker 使用的防火墙后端；nftables 后端需要对应 nft 规则。将自定义规则放入服务器的 Docker 启动后任务，容器地址变化后重新应用；不要在生产机器直接恢复一整份过期 Docker iptables 快照。

部署验证应包含：正常公网测试资源可下载，重定向到 `127.0.0.1`、NAS 地址或 `169.254.169.254` 的测试地址失败，且应用仍能查询下载器 RPC。规则不会为模型接口、数据库或其他现有应用改变出站策略。

## 默认重试策略

| 项目 | 默认值 |
| --- | --- |
| 同一资源重试 | 最多 2 次，分别等待 30 秒、120 秒 |
| HTTP 无进度 | 5 分钟 |
| BT 无进度 | 10 分钟 |
| AI 重新搜索 | 最多 3 轮 |
| 不同资源尝试 | 最多 5 个 |

排队、暂停和校验阶段不算下载停滞。硬盘/NAS 离线、空间不足或下载器断线时等待基础设施恢复，不消耗换源预算。失败的 BT 资源按 infohash 去重，换了链接但内容相同也不会反复尝试。不同资源使用不同临时目录。

任务状态、尝试记录和预算存入 MySQL。重启后先对账下载器已有任务；提交请求超时后使用原来的 tag/GID 查询，避免盲目重复提交。下载完成后校验文件并移入最终目录。取消任务保留已有文件，不自动删除用户数据。

## 对接 API

继续使用现有账号 Bearer Token，接口位于 `/api/v1`。主应用设置了入口前缀时使用其实际公开路径。

| 接口 | 用途 |
| --- | --- |
| `GET/POST /storage-locations` | 查看、登记存储位置 |
| `POST /storage-locations/{id}/probe` | 检查挂载、权限和剩余空间 |
| `GET /files?storage_id=…&path=…` | 查看目录 |
| `GET /files/download?storage_id=…&path=…` | 下载文件 |
| `GET/PUT /media/config` | 搜索源和下载器设置 |
| `GET /media/status` | 后台 worker 在线状态 |
| `POST /anime/search` | 单次资源搜索 |
| `GET/POST /downloads` | 列表、创建持久下载任务 |
| `GET /downloads/{id}` | 任务详情 |
| `POST /downloads/{id}/actions` | `pause` / `resume` / `cancel` / `retry` |
| `GET /downloads/{id}/events?after=序号` | 补读持久进度事件 |
| `GET /downloads/{id}/stream` | SSE，支持 `Last-Event-ID` |
| `GET/POST /agent-runs` | 查询、创建内部 AI 任务 |
| `GET /agent-runs/{id}` | AI 步骤与子任务 |
| `POST /agent-runs/{id}/cancel` | 取消 AI 任务 |

创建下载任务示例：

```json
{
  "request_key": "client-generated-unique-request-id",
  "storage_id": 1,
  "requirement": {
    "title": "番剧名称",
    "aliases": ["另一个名称"],
    "season": "2",
    "episode": "3",
    "quality": "1080p",
    "subtitle": "简中"
  }
}
```

同账号重放相同 `request_key` 返回已有任务。客户端需要存储最近事件序号，在断线后续读；不要因为网络超时重新生成任务。页面中显示的来源 URL 会去除查询参数，下载所需签名只保留在服务器。

WebSocket 使用独立的 `/api/v1/download-events/ws`，不会被聊天生成阻塞。连上后 10 秒内发送 `{"type":"auth","token":"账号令牌"}`，收到 `ready` 后发送 `{"type":"subscribe","task_id":1,"after":0}`。省略 `task_id` 可订阅当前账号全部下载任务。事件的 `seq` 是续传游标，断线后用最后收到的序号重连。发送 `{"type":"download.action","task_id":1,"action":"cancel"}` 可控制任务，`{"type":"ping"}` 用于探活。令牌仅在首帧发送，不放在 URL。

普通账号由管理员分配独立目录和下载器：登记存储及保存下载器配置时填写 `owner_id`（后台也有“用户 ID”选项），省略则归当前账号。不同账号不能登记相互包含的目录。管理员为其他账号补充一种下载器时保留另一种已有连接；密码/API Key 留空保留原值，页面不显示已保存密钥。备份恢复时保留原 `SECRET_KEY`，否则需重新填写已加密的下载器和 RSS 凭据。

内部代理每轮搜源默认最多使用 12 次模型调用、24 次工具调用、3 个子代理，整个任务树共享预算；子代理不能进一步分派。暂停/重启不重置预算。通用后台调查可向 `POST /agent-runs` 发送 `{"prompt":"调查内容","request_key":"客户端唯一标识"}`，允许的工具限定为联网搜索、网页阅读和当前账号文件目录查看。

完成及需处理消息发送到账号默认通知渠道，可在设置中选飞书应用、Webhook 或通知组。单个渠道失败会重试，最多 5 次，已送达渠道不重复发送；进程在外部发送成功但写入记录前退出时，接收方仍可能看到一次重复通知。

## 当前范围

支持能从公开页面、RSS 或用户明确提供的资源地址解析出的下载资源。不会绕过登录、验证码、付费权限或 DRM；也不会运行来源网页里的脚本。当前 HTTP 适配器下载普通文件，不拼接 HLS/DASH 流。启用多个来源可以提高找到替代资源的机会，但无法保证每一部番剧或每一个链接都可下载。

应用、下载器和 NAS 的目录必须映射到同一实际存储；不能仅填写一个 SMB 地址让应用自动挂载。独立 worker 必须持续运行；只启动网页服务无法持续监控下载。
